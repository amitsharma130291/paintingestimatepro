## Free tools: estimate template, interior calculator, job-cost calculator

**Verdict: ready**, with one integrity fix this session.

- The free estimate template previously claimed **"saved locally in your browser" even when the save had silently failed** (a full storage quota, or private browsing blocking `localStorage` entirely) — a real risk of a customer losing estimate data while believing it was safe. Fixed: the UI now reports the truth, offers a working **Retry** action, and preserves a corrupted stored value's original bytes under a backup key rather than silently discarding them. Live-verified in the browser with a monkey-patched throwing `localStorage.setItem`.
- All three tools' core calculation paths remain covered by pure-logic test modules with independently-derived oracle fixtures, unchanged from v3's verdict.
- **Known, disclosed, non-blocking gaps** (unchanged from v3, not addressed this session): the free interior calculator has no ceiling-only mode, no quick/detailed opening-entry switch, and no additional prep-labor line (`INT-008/009/010/014`). These are scope gaps, not correctness defects in what's shipped.

## Payment / access readiness (Dodo Payments)

**Verdict: two serious security defects found and fixed this session; implementation is now believed correct, but still has never processed a real transaction.**

- **ACCESS-013 (serious, security) — entitlement was never bound to the configured product.** `verify.ts`, `redeem.ts`, and the payment webhook all granted access for ANY successful Dodo payment, never checking it actually purchased Painting Estimate Pro's product. A real successful payment for an unrelated product (or a different/legacy price) on the same Dodo merchant account would have unlocked the $99 tier for free. Fixed with a single shared `evaluatePaymentEntitlement()` decision used identically across all three code paths, tested by driving the REAL API route handlers with a mocked Dodo SDK (34 new tests).
- **ACCESS-014 (serious, security) — a network failure let a fabricated local record unlock access permanently.** `verifyAccess()` returned the raw, fully attacker-editable `localStorage` payment record whenever the live check hit a network failure. Reproduced with the task's own exact scenario (an invented payment ID + a simulated network outage) and confirmed it granted access. Fixed: `checkAccess()` now reports a distinct "unavailable" status on a network failure — never access, but the stored record and all local project data are preserved for a legitimate retry. Live-verified in the browser both before and after.
- **v3's ACCESS-002 fix (a real server response fails closed) remains correct and is re-verified** by the rewritten test suite — its guarantee wasn't broken by this session's changes, just extended.
- **What is still NOT yet true**: no real Dodo product, API key, or webhook secret is configured (by necessity — these are the user's own dashboard credentials). Nothing has processed a real or even a real test-mode transaction. `ACCESS-001/003/004/008` remain genuinely blocked on this — a concrete external dependency, not unfinished code.
- **Before accepting a real charge, the user must**: (1) create the Pro product in the Dodo dashboard, (2) supply the resulting credentials to `.env`/the real deployment per `.env.example`, (3) run at least one real test-mode purchase through the complete flow (checkout → verify → redeem-on-a-second-device → refund → re-verify access is revoked, AND — new this session — confirm a purchase of a *different* product on the same account does NOT unlock Pro), and (4) decide when to update the homepage's "planned" copy — a marketing decision, not a code one, deliberately left untouched.
