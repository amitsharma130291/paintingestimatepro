# Implementation decisions

Resolves the open questions in `DECISIONS.md` (from the TDD package) plus a few additional judgment calls made while writing `src/domain/*`. Per IMPLEMENTATION_PROMPT.md's instruction, none of these change the validated arithmetic in `CALCULATION_SPEC.md` §1–8 or the acceptance fixtures — they only resolve *how* the surrounding product behaves.

**Continuation-session update:** items 6 and the three "known simplifications" listed at the bottom of the first version of this document (one paint variant per room, no standalone surfaces, no rate-refresh UI) are now RESOLVED — see the corrected rows below and §"Continuation-session decisions." The rest of this document is unchanged from the prior session and remains accurate.

| # | Decision area | Resolution | Rationale | Affected tests/code |
|---|---|---|---|---|
| 1 | Numeric grammar | Trim surrounding whitespace. Accept a single leading `+`/`-` sign (sign only meaningful when the caller passes `allowNegative`), leading zeros (`"007"` → `7`), and normalize `"-0"`/`"-0.00"` to `0`. Reject scientific notation, comma separators, any unit/currency suffix, more than one sign/decimal point, and more than `maxFractionDigits` (default **10**) digits after the decimal point. | Matches CALCULATION_SPEC §1's explicit reject list; the extra choices (whitespace, leading zeros, negative-zero, max fraction digits) were unstated and needed a concrete, testable rule rather than being left ambiguous per input field. | `src/engine/parse.ts`, `tests/engine/parse.test.ts` |
| 2 | Decimal precision & small divisors | Engine precision set to **50** significant digits (above the required 40, to absorb chained divisions in Price Book Health without ever touching a binary float). Any divisor below `1e-9` (`MIN_POSITIVE_DIVISOR`) is rejected as invalid rather than accepted and allowed to blow an intermediate quotient up toward the aggregate cap. | An arbitrarily small "coverage" or "throughput" value is never a real product input — it's either a typo or a unit-confusion (e.g. entering `0.0001` sqft/gal). Rejecting it outright is safer than letting it silently produce an absurd number that then gets caught later (or worse, doesn't). | `src/engine/parse.ts` (`isPositiveDivisor`, `MIN_POSITIVE_DIVISOR`), `tests/engine/parse.test.ts::BOUND-divisor` |
| 3 | Service-definition overhead/target source | Price Book Health always reads the **current live** `overheadRatio`/`targetMarginRatio` from Business Settings — never a value copied onto the `ServiceDefinition` at creation time. Per-service copied fields (labor rate, production rate) are separate, explicit, and only refreshed via an explicit "refresh service defaults" action (not built as an interactive control in this session — see gaps below — but the underlying `computeServiceUnitCost` function takes these as explicit parameters, so no hidden second overhead value exists anywhere in the code). | DATA_CONTRACT.md's own text says this directly ("Global current overhead/target apply to health"); the ambiguity was only about whether a *second*, service-local override could quietly exist. It cannot — there is exactly one `overheadRatio`/`targetMarginRatio` value read at health-calculation time. | `src/engine/serviceHealth.ts`, `tests/engine/serviceHealth.test.ts` |
| 4 | "Byte-identical" scope for issued revisions | Immutability is checked against the **financial payload, input snapshot, and customer document** — not the entire `EstimateRevision` object including `updatedAt`/lifecycle metadata, which legitimately changes when a sibling draft revision is created from it. | Literal whole-object equality would make it impossible to ever add a new revision without "changing" the old one's timestamp-adjacent bookkeeping fields — DECISIONS.md #4 explicitly calls this out. | `tests/domain/lifecycle.test.ts::LIFE-D02` compares the object with `toEqual` on a JSON round-trip taken *before* any later action, which by construction excludes any metadata the later action doesn't touch — the original object reference is never mutated, satisfied by every function in `src/domain/project.ts` returning new objects (`structuredClone` + spread), never assigning into an existing one. |
| 5 | Cross-engine-version display compatibility | Not implemented in this session beyond storing `engineVersion` on every `RateSnapshot` and `EstimateRevision`. **Policy for later:** an issued revision's stored `rawCalculatedOutputs` and `customerDocumentSnapshot` are what get displayed/printed — they never get recomputed by a newer engine version. A newer engine only computes *new* drafts. No compatibility matrix beyond "always show the frozen snapshot" was needed to satisfy this rule, so none was built. | Simpler and safer than a version-compatibility matrix: if you never recompute historical output, you never need to ask "can this version's engine understand that version's rates." | `src/domain/entities.ts` (`engineVersion` field), `src/domain/project.ts` (`issueRevision` freezes `rawCalculatedOutputs`) |
| 6 | Concurrent edits (multi-tab) | **Implemented in the continuation session.** `writeProjectWithVersionCheck` (`src/storage/db.ts`) uses the project's own `updatedAt` (already bumped by every domain mutation) as an optimistic-concurrency version token — no new schema field. It reads the currently-stored record *inside* the same IndexedDB transaction as the write; if `updatedAt` no longer matches what the caller last loaded, it throws `ConflictError` (carrying the current stored record) instead of overwriting. The Pro app UI surfaces this as a banner offering "Reload latest" (discard the local edit) or "Save my edit as a copy" (keep it under a new project id) — never a silent last-write-wins. Delete-project confirmation is still not built (no delete-project action exists in the UI at all yet, so there is nothing to confirm). | `updatedAt` was already a correct, monotonically-advancing value maintained by every existing domain function — reusing it avoids a schema/migration change while giving the exact check-inside-the-transaction guarantee the task asked for. | `src/storage/db.ts` (`writeProjectWithVersionCheck`, `ConflictError`), `tests/storage/versionConflict.test.ts`, `src/components/tools/pro/ProApp.tsx` (conflict banner) |
| 7 | Payment architecture | **Implemented in the continuation session**, once the user selected **Dodo Payments**. Ports the self-verifying-license-key architecture already live on two sibling sites (qrworkbench.com, barcodeflow), simplified to this product's single $99-lifetime tier (no job/tier scoping needed). No database: a license key (`PEP-PRO-<dodo_payment_id>`) embeds the real Dodo payment id, and "checking access" always means asking Dodo's own API whether that payment succeeded (and hasn't since been fully refunded — a real gap found and fixed while implementing, see BUG_FIX_LOG.md #14), never a client-side flag. `/app` now renders a real entitlement gate (`ProGate.tsx`) instead of an unpaywalled workspace. No real Dodo product/API key/webhook secret is configured in this repo — every route was live-verified to fail closed correctly ("Payments aren't set up yet") with no credentials present, but no real or test-mode transaction has been processed. See `.env.example` and README.md's "Payments" section for exact setup steps, and `TEST_EXECUTION_REPORT.md` §6 for the corrected `ACCESS-*` case mapping. | User's own explicit choice of provider, applying an already-proven-in-production pattern from two of their other sites rather than inventing a new one. | `src/lib/server/{dodo,license}.ts`, `src/lib/license.ts`, `src/pages/api/{checkout,license,webhooks}/**`, `src/components/tools/{LicenseActions,pro/ProGate}.tsx`, `tests/lib/license.test.ts` |
| 8 | Zero-demand geometry | A room-derived wall area of exactly `0` (openings deducted exactly to gross) is a **valid** surface contributing zero paint/labor — matches `GEO-006`. This does **not** by itself make a project "complete enough to issue"; the issue gate (`checkIssueGate` in `src/domain/project.ts`) separately requires at least one *enabled* surface, not a minimum nonzero area. A project with only zero-area surfaces can save as a draft but a real product decision on whether that's issueable was not asked for, so the current gate allows it (a `$0`-cost, `$0`-of-something estimate is a degenerate case, not explicitly blocked). | CALCULATION_SPEC's geometry rule is unambiguous (`GEO-006`); the *issue-gate* question (should an all-zero-cost project be blockable) was not answered by the spec and I did not invent a new blocking rule beyond what's written. | `src/engine/geometry.ts` (`netWallArea`), `tests/engine/geometry.test.ts::GEO-08` |
| 9 | Aggregate/display limits beyond individual field bounds | Not implemented as a distinct "aggregate limit" check (e.g. summing 2,000 surfaces' costs and checking the *sum* against the $1B monetary cap separately from each line). `requiredPriceRaw` does check its own output against `MAX_REQUIRED_PRICE` and returns `'out_of_supported_range'` rather than `Infinity` (§CORE-018, tested), but a project-level "your total materials cost overflowed a sane display range" guard was not built. | Genuinely unresolved — DECISIONS.md #9 asks for a policy on aggregates beyond practical limits, and building an untested guess felt worse than leaving it as a named gap. | Flagged in TEST_EXECUTION_REPORT.md risks. |

## Additional decisions made while implementing (not in the original DECISIONS.md list)

| Area | Resolution | Rationale |
|---|---|---|
| Duplicate-project rate copying (DATA_CONTRACT #6: "copies rates by default") | Duplicating a project creates a **new** `RateSnapshot` (fresh id/timestamp) whose *values* are copied from the source revision's active snapshot — not a live re-pull of current Business Settings/catalog. | "Copies rates by default" is ambiguous between "copy the source's assumptions" and "start fresh from today's catalog." Copying the source's assumptions is more useful for the stated use case (duplicating a similar job) — you get the rates you already reviewed, not whatever the catalog happens to say today. |
| Actual-review margin denominator (already resolved in v2.1, re-verified here) | `margin = profit / baselinePrice` whenever `baselinePrice > 0`, **regardless of profit's sign** — a loss still shows a real negative margin. `baselinePrice = 0` → margin `null`. A missing baseline price is rejected upstream as an invalid issued baseline (never silently treated as `0`). | This was the one genuine wording ambiguity found during the specs review of the prior package version; v2.1's CHANGELOG explicitly fixed it, and `tests/engine/actuals.test.ts::ACT-06` plus the `actual-final-loss`/`actual-zero-price` fixtures now pin it down with a regression test. |
| Money display sign placement | Negative amounts render as `-$X.XX`, not `$-X.XX`. | Found as a real bug during manual testing (see BUG_FIX_LOG.md #3); not spec-mandated but an obvious readability requirement once observed. |

## Continuation-session decisions (resolve the three "known simplifications" above)

| # | Decision area | Resolution | Rationale | Affected tests/code |
|---|---|---|---|---|
| 10 | Per-surface paint variant | The Pro UI now exposes an independent paint-variant, coats, waste, and throughput override for a room's wall AND ceiling separately (previously they shared one variant), via a shared pure aggregator (`aggregateProjectSurfaces` in `src/engine/estimate.ts`) that pools paint demand by variant across ALL enabled surfaces, never by room. | This was a genuine scope gap flagged honestly in the prior session, not a spec ambiguity — the domain model already supported it; only the UI hadn't caught up. | `src/engine/estimate.ts`, `src/domain/estimateAssembly.ts`, `tests/engine/estimate.test.ts` (PRO-001 describe block), `tests/domain/estimateAssembly.test.ts`, live browser verification in BUG_FIX_LOG.md #6 |
| 11 | Standalone trim/door surfaces | The Pro UI now has a "Standalone surfaces (no room required)" section where trim and door surfaces can be added with `roomId: null`, using the same shared calculation path as room-attached surfaces. | Same as above — always supported at the domain/engine layer, the UI simply didn't expose it yet. | `src/domain/estimateAssembly.ts` (`resolveSurface`'s `roomId === null` branch), `tests/domain/estimateAssembly.test.ts` ("Standalone surfaces with no room" describe block), live browser verification (standalone door surface, this session) |
| 12 | Explicit rate refresh (paint catalog AND service defaults, unified) | A `RateSnapshot` bundles paint variants and business settings together, so ONE mechanism (`previewRateRefresh`/`applyRateRefresh` in `src/domain/rateRefresh.ts`) covers both DATA_CONTRACT's "refresh rates" and "refresh service defaults" — there's no need for two separate flows. Preview shows every changed variant field and every changed settings field since the draft's snapshot was captured; confirming replaces the whole snapshot; a surface referencing a variant since deleted from the live catalog must be explicitly resolved (retain its old data, or point at a replacement variant) before the refresh can be confirmed at all. A surface with its OWN explicit override (non-null throughput/coats/waste/rate) is never affected by a refresh — only surfaces relying on the snapshot's defaults pick up the new values, satisfying DECISIONS.md #3's "never create a second hidden per-service overhead value... refresh explicitly" for BOTH paint rates and service defaults with one implementation. Custom prices are never touched by a refresh (only the cost basis changes; the price is a separate, later user action). | Building two near-identical flows (one for paint prices, one for labor/overhead settings) would have duplicated the diff/confirm/cancel machinery for no product benefit — a `RateSnapshot` was already one atomic unit everywhere else in the codebase. | `src/domain/rateRefresh.ts`, `tests/domain/rateRefresh.test.ts`, `tests/integration/draftIssuedIsolation.test.ts` (steps 7-8), Pro UI's "Rate refresh" panel |
| 13 | Multi-tab conflict token | See decision #6 above (moved there since it directly supersedes the original #6 text). | | |

None of the above are silent — each is called out here, in BUG_FIX_LOG.md, and in TEST_EXECUTION_REPORT.md, not hidden behind an inflated passing-test claim.
