# Decision register and limits

The v2.1 contract remains authoritative. Test design exposed a few implementation-policy questions. Do not turn guesses into passing tests.

1. **Browser numeric grammar**: v2.1 rejects malformed/mixed-unit text but does not settle trimming surrounding whitespace, leading plus, scientific notation, comma locale entry, leading zeros or negative zero. Before parser implementation, record accept/reject behavior and canonical normalization for each. Recommended: trim whitespace, accept ordinary signed-free decimals with leading zeros, normalize negative zero to zero only if deliberately accepted, reject exponent/comma/unit syntax with guidance. Recommendations are not silently binding. Add one case per accepted/rejected variant.
2. **Decimal precision**: engine precision >=40 is specified, but maximum fractional input digits and extraordinarily small positive divisors are not. Set supported input precision and output-size guard before building expensive arithmetic; do not truncate meaningful quantities silently. Validate exact ceiling boundaries and price cap through public API.
3. **Service defaults wording**: DATA_CONTRACT mentions copied labor/overhead defaults but then explicitly says global current overhead/target apply to health. Treat live global overhead/target as authoritative per CALCULATION_SPEC §8; copied service labor/production overrides refresh explicitly. Do not create a second hidden per-service overhead value.
4. **Original bytes vs metadata**: issue/supersede and timestamps legitimately change lifecycle metadata. Compare frozen financial payload, input/rate snapshot and customer document for immutability; don't require the entire project JSON hash to remain identical while adding revisions/actuals.
5. **Unknown engine display compatibility**: import schema2 alone does not establish ability to display all engine versions. Specify a supported engine-version policy; never recalculate historical values just to force compatibility.
6. **Concurrent edits/deletion**: conflict handling for multiple tabs and project-deletion confirmation are recommended hardening beyond explicit v2.1 detail. Decide before enabling those actions; test chosen behavior without changing financial formulas.
7. **Payment architecture**: provider, signature format, offline grace, device policy, refunds and recovery remain unresolved. ACCESS cases are release scenarios; bind them to current provider documentation after selection. Do not write assertions against guessed provider payloads.
8. **Zero-demand geometry**: derived net wall area0 is valid when openings exactly match gross. Manual area has the positive-geometry constraint. Zero counts/length can pass field validation but do not automatically establish a meaningful complete project. Use issue gates, not a hidden minimum charge.
9. **Calculated aggregate limits**: inputs have bounds; required selling price has a $1bn cap. Define how aggregates beyond practical display/storage limits are reported, even when individual rows pass limits. No overflow/NaN or silent saturation is acceptable.

   **RESOLVED** (requirements AGG-001 through AGG-006, `TOOL_REQUIREMENTS_MATRIX.csv`; implemented in `src/domain/estimateAssembly.ts`, `src/engine/actuals.ts`, `src/engine/parse.ts`): every COMPUTED aggregate this session identified as reachable even when every contributing field individually passes its own bound -- paint demand, purchased gallons, materials cost, labor hours, labor cost, direct cost, overhead, estimated job cost, a suggested/required price, a custom entered price, profit, an actual-cost total, and a customer-document monetary total -- shares one deterministic policy:

   - **Supported maximums.** Reuses the exact figures DECISIONS.md #9 itself already names, rather than inventing new ones: `MAX_AGGREGATE_MONETARY` = $1,000,000,000 (identical to `MAX_MONETARY_INPUT`/`MAX_REQUIRED_PRICE`, applied here to a computed SUM/PRODUCT rather than a single entered field) governs every monetary aggregate (materials, labor cost, direct cost, overhead, job cost, suggested/required price, custom price, profit-implying totals, actual-cost totals, customer-document totals). `MAX_AGGREGATE_HOURS` = 1,000,000 hours (identical to the per-line `MAX_HOURS`) governs total project labor hours. `MAX_AGGREGATE_GALLONS` = 1,000,000,000 gallons governs both raw paint demand and purchased gallons per variant.
   - **Immediately below the boundary.** A genuinely complete, priced result -- no different from any other in-range calculation.
   - **Exactly at the boundary.** Still accepted (every check uses a strict `>`, never `>=`) -- confirmed by dedicated boundary tests in `tests/domain/aggregateLimits.test.ts` and `tests/domain/boundaryMatrix.test.ts`.
   - **Immediately above the boundary.** `assembleProjectEstimate` returns `calculationState: 'invalid'` with `outOfSupportedRange: true` and a specific, human-readable reason naming which aggregate exceeded which ceiling; `evaluateActualReview` returns `state: 'out_of_supported_range'`. Neither ever exposes `Infinity`, `NaN`, a silently-saturated/clamped value, or a value silently rounded back into range -- every affected numeric field is `null`, exactly like any other invalid/incomplete result, never a partial or approximate number.
   - **Draft-saving behavior.** Unaffected. `calculationState`/`outOfSupportedRange` are ordinary fields on a perfectly normal, storable `EstimateRevision` -- `saveDraft()` never gates on them (matching CORE-028's pre-existing "draft-saving is unconditional" guarantee). A user can always save and return to an out-of-range draft to correct it.
   - **Issue-gate behavior.** Blocked. `checkIssueGate` already requires `calculationState === 'complete'`; an out-of-range result is `'invalid'`, so it is rejected with the same "Estimate is not complete" reason as any other invalid calculation -- no separate gate needed.
   - **Display behavior.** The Pro estimate summary and the free tools' own error containers render the specific reason text inside a `role="alert"` region (never a silent visual-only cue -- see UX-003); no calculation-result row ever renders alongside an out-of-range message, so a plausible-looking number can never sit next to it.
   - **Storage and backup behavior.** An out-of-range draft is stored exactly like any other invalid draft (see draft-saving above); `exportBackup`/backup validators do not special-case it -- the numbers involved are ordinary (if large) decimal strings, never `Infinity`/`NaN` literals that would break JSON serialization.
   - **Imported-data validation.** No separate import-time numeric re-validation was added: a DRAFT revision arriving via import is re-validated the moment it is next recalculated (the same `assembleProjectEstimate` chokepoint every draft already goes through) -- there is no parallel/second validation path to keep in sync. An ISSUED (frozen) revision is never recalculated at all (see below), so import never rejects historical data for exceeding a ceiling that did not exist when it was created.
   - **Frozen issued-output compatibility.** Exempt, by the same principle as BACK-026's engine-version gate: `buildCustomerDocument`/`readFrozenCalculatedOutputs` never re-derive or re-validate a frozen revision's numbers -- an already-issued document with a total that would exceed today's ceiling (for example, one created under an older build with no ceiling at all) still renders exactly as recorded, confirmed by a dedicated test.

   Two genuine implementation gaps were found and fixed while building this policy (not merely a missing check): (1) a custom entered price had no upper field bound at all, so an absurd custom price was previously accepted as a "complete," issueable calculation; (2) the SUGGESTED-price path could silently report `calculationState: 'complete'` with `price`/`effectivePrice` both `null` whenever the required price itself exceeded the pre-existing `MAX_REQUIRED_PRICE` ceiling at an extreme (but individually valid, `<1`) target margin -- exactly the disguised-invalid state this decision forbids. Both are now `outOfSupportedRange` results instead.

These are implementation clarifications, not reasons to change the validated arithmetic fixtures. Keep issue-level decisions in version control before corresponding tests become release gates.
